## 1. 需求来源

用户提出开放「与 GLaDOS 对接的 Shimeji 克隆功能」，同时带出两个必须先定清的语义问题：

1. **用户选中哪个 Shimeji 实例可以对话？还是随便点哪个都可以对话？**
2. **GLaDOS 发出的事件如何映射 Shimeji 动作？所有 Shimeji 实例都需要响应吗？**

本文件的目的是：先把两个仓库的**真实现状**调研清楚，把问题拆成可决策的选项，给出推荐方案与协议设计，供评审拍板后再进入开发。

## 2. 现状调研（代码事实）

> 以下结论均来自源码走读，附文件与行号锚点，便于复核。

### 2.1 Shimeji 侧：多实例（克隆）能力

| 事实 | 证据 |
|---|---|
| 每个角色是一个 `Mascot` 对象，各持一个透明窗口（JNA） | `Mascot.java:54-70`（`window = NativeFactory...newTransparentWindow()`） |
| `Mascot` 有进程内自增 ID，但**是 private，且不对外暴露** | `Mascot.java:64` `private final int id;`、`:69` `private static AtomicInteger lastId` |
| `toString()` 返回 `"mascot"+id`，是当前唯一的 ID 表达 | `Mascot.java:192-195` |
| 自主增殖由两个行为触发：`SplitIntoTwo`（→ `Divide1`）、`PullUpShimeji`（→ `PullUpShimeji1`），底层是 `action/Breed` | `conf/behaviors.xml:58,98`；`action/Breed.java` |
| **托管模式下这两个增殖行为被逻辑层禁用** | `glados/GladosManagedConstraints.java:30-38`（`BREEDING_BEHAVIORS` 集合 + `isBreedingBehavior`），由 `Configuration.isBehaviorEnabled` 调用 |
| 但 GLaDOS 主动下发的 `createMascot` 走 `Main.createMascot()`，**不受该约束影响** | `GladosBridge.java:createMascot()`、`Main.java:createMascot(String)` |
| 增殖上限由行为条件 `mascot.totalCount < 50` 控制 | `conf/behaviors.xml:58,98` |
| `setRole` 语义 = `disposeAll()` + `createMascot()`（**清空后只留一个**） | `GladosBridge.java:setRole()` |
| `remainOneOnly(imageSet)` 按**角色名（imageSet）**保留，不按实例 | `Manager.java:remainOneOnly(String)` |
| `setBehaviorAllByName(name, imageSet)` 只支持按**角色名**过滤，**无实例级寻址** | `Manager.java:setBehaviorAllByName(String,String)` |

**结论 A**：Shimeji 引擎天然支持多实例（`Manager.mascots` 是 List），但**当前没有任何对外可寻址的实例标识**，所有控制命令的最小粒度是「角色（皮肤）」，不是「实例」。

### 2.2 Shimeji 侧：状态上报与事件

| 事实 | 证据 |
|---|---|
| `GET /status` 返回 `mascots` 数组，每项仅 `{x,y,width,height}`，**无 id / 无 role / 无 behavior** | `GladosBridge.java:buildStatusBody()` |
| 左键点击（非拖拽）上报事件 `click`，**不带任何实例标识** | `Mascot.java:281` `GladosEventReporter.report(EVENT_CLICK)` |
| 角色移动上报 `move`，payload `{x,y,width,height}`，**不带实例标识**，带 200ms/2px 节流 | `Mascot.java:572`、`GladosEventReporter.reportMascotMove()` |
| 事件落盘为 `<glados-home>/glados-events/<ts><seq>-<type>`，内容 `type\npayload` | `GladosEventReporter.report()` |
| 托管模式下右键菜单被完全禁用（不弹原版菜单） | `Mascot.java:245-252`（`isManagedProcess()` 时右键直接 return） |

**结论 B**：事件通道是「匿名」的——宿主只能知道"有某个角色被点了"，不知道"是哪个"。

### 2.3 GLaDOS 侧：行为下发与事件消费

| 事实 | 证据 |
|---|---|
| `send('setBehavior', {behavior})` **不传 role** → 桥内 `setBehaviorAllByName(name, null)` → 应用到**全部实例** | `shimeji-bridge.js:send()`、`GladosBridge.setBehavior()` |
| 任务状态 → 行为的映射表（presentation/attention/taskState → AIWorking 等） | `shimeji-bridge.js:behaviorForSnapshot()` |
| 瞬时行为（AIReview/AINotify/AIAck/AIBlocked/AIOffline）走独立队列，最多 8 条、TTL 30s | `shimeji-bridge.js:playTransient()` |
| 稳态行为有 500ms 去抖 + 1500ms 最小驻留 | `shimeji-bridge.js:DEBOUNCE_MS/MIN_DWELL_MS` |
| 消费 `glados-events`：`click` → `onShimejiClick()` → `openChat()`（**全局单例对话窗口**） | `controller.js:2296-2364` |
| `move` → `applyShimejiMove()`，把 `shimejiMascots` **覆盖为单元素数组** | `controller.js:2341-2349` |
| 气泡定位只取 `shimejiMascots[0]` | `controller.js:1959-1960` |
| `sendControl` 有命令白名单 `COMMANDS` | `shimeji-manager.js:278-292` |

**结论 C**：GLaDOS 侧完全按「单实例」心智实现——气泡只跟第一个、点击只开同一个对话、行为全局广播。多实例会立刻暴露两个问题：**气泡乱跳取 first、点谁都是同一个对话**。

### 2.4 两侧能力对比矩阵

| 维度 | Shimeji 侧 | GLaDOS 侧 | 缺口 |
|---|---|---|---|
| 实例标识 | 有内部 id，未暴露 | 无实例概念 | **需统一 ID 体系** |
| 状态查询 | `mascots[]` 无 id/role/behavior | 只读 `mascots[0]` | 需补字段 + 多实例消费 |
| 行为下发 | 支持按 role 过滤 | 不传 role（全局） | 需 `target` 寻址 |
| 事件上报 | click/move 匿名 | 收到即当单实例处理 | 需事件带 id |
| 克隆入口 | 自主增殖被禁；`createMascot` 可用 | 无克隆 UI/命令 | 需设计克隆产品形态 |
| 对话归属 | 无 | 全局单窗口 | **需决策** |

## 3. 两个核心问题的拆解与决策

### 3.1 问题一：点哪个实例都能对话吗？

#### 现状
`onShimejiClick()` 直接调用 `openChat()`，而 `openChat()` 是全局单例（`this.chatWindow` 已存在则 `show()+focus()`）。所以**当前是"随便点哪个都打开同一个对话窗口"**，且对话内容与"被点的是谁"无关。

#### 可选方案

| 方案 | 行为 | 优点 | 缺点 |
|---|---|---|---|
| **A. 全局单对话（现状）** | 点任意实例 → 同一个 chatWindow | 实现零改动；会话模型简单 | 用户无法区分"跟哪个分身说话"；多实例时语义错乱 |
| **B. 每实例独立会话** | 每个实例绑定独立 `sessionId` + 独立对话窗口 | 语义最清晰，符合"分身"直觉 | 多窗口管理、多会话并发、上下文成本；50 实例不可行 |
| **C. 单窗口 + 实例上下文切换（推荐）** | 只保留一个对话窗口；点击某实例即把该窗口"绑定"到该实例的会话，切换而非新建 | 既满足"点谁跟谁说话"，又不炸窗口；可扩展到多实例 | 需实现"实例 ↔ sessionId"映射与切换逻辑 |
| **D. 主实例对话 + 分身只做表现** | 只有主实例可对话，其他实例点击只播动画/气泡回应 | 最简单可控 | 分身点击"没反应"体验割裂 |

#### ✅ 决策：**A（全局单对话，保持现状）**
> 2026-11-26 用户拍板。

- 点击**任意**实例 → 打开同一个全局对话窗口（`this.chatWindow`），与"点的是哪个实例"无关。
- 对话内容不区分分身，所有实例共用一个 AI 会话。
- **实现成本最低**：GLaDOS 侧 `onShimejiClick()` → `openChat()` 保持原样，**无需实例 ↔ sessionId 映射**。
- 语义约定（需在 UI/文档中说清）：桌宠分身是"同一人格的多个身体"，不是多个独立助手；跟哪个分身说话都是跟同一个 GLaDOS 说话。
- 由此简化：气泡定位仍取"当前活跃/主实例"，但对话归属不随实例变化。

> 影响：FR-4 从"实例会话切换"简化为"全局单会话 + 气泡跟随主实例"（见 §4.4）。

### 3.2 问题二：事件如何映射动作？所有实例都要响应吗？

#### 现状
- **稳态行为**（AIWorking/AIWaiting/AIFailed…）：`setBehavior` 不传 role → 广播到**全部实例** → 所有分身同时走路/同时趴下。
- **瞬时行为**（AIReview/AINotify…）：同样广播。
- 结果：多实例时视觉上"整齐划一"，失去分身的自然感，且 50 实例同时播动画有性能压力。

#### 可选方案

| 方案 | 行为 | 优点 | 缺点 |
|---|---|---|---|
| **A. 全量广播（现状）** | 所有实例响应同一行为 | 实现简单，状态一致 | 视觉僵硬；性能差；丧失分身差异 |
| **B. 仅主实例响应** | 只有 primary 播 AI 行为，分身保持自主树 | 自然、省性能 | 分身"不参与"，AI 状态感知弱 |
| **C. 主实例 + 分身弱化响应（推荐）** | primary 播完整行为；分身播"弱化变体"或按概率/延迟响应 | 兼顾表现力与性能 | 需定义"弱化变体"映射 |
| **D. 分组/角色感知** | 按 role 或分组，每组一个代表响应 | 适合多角色混养 | 复杂度高，首期不必 |

#### ✅ 决策：**C（primary 完整 + 分身弱化）**
> 2026-11-26 用户拍板。

分三层规则：

1. **稳态行为（AIWorking/AIThinking/AIWaiting/AIFailed/AIDisconnected/AIIdle）**
   - primary：完整播。
   - 分身：按 `followerResponse` 策略——
     - `mirror`（默认，≤3 个实例时）：同步播，保持"合体感"；
     - `sample`（>3 个实例时）：按 50% 概率 + 0~800ms 随机延迟响应，避免整齐划一；
     - `ignore`（可选）：只 primary 播。
   - 实现上仍是同一行为名，靠 `target` 参数 + 分身侧延迟/概率控制，**不新增行为**。

2. **瞬时行为（AIReview/AINotify/AIAck/AIBlocked/AIOffline）**
   - 默认只作用于 **primary**（庆祝/通知应由主角承担，避免 50 个一起蹦）。
   - `target: "nearest"` 可选：由"离鼠标最近的实例"响应（需 Shimeji 上报坐标已具备）。

3. **前沿/兜底**
   - 若实例数与性能冲突（如低配机 + 20 个实例），自动降级为 `sample` 或 `ignore`。

## 4. 功能需求

### 4.1 FR-1 实例标识体系（基础能力）

- **FR-1.1** `Mascot` 暴露只读 `getInstanceId()`，格式 `mascot-<id>`（`id` 为进程内自增，重启重置）。
- **FR-1.2** `GET /status` 的 `mascots[]` 每项补齐：`id`、`role`（短名）、`behavior`（当前行为名）、`paused`。保持 `x/y/width/height` 向后兼容。
- **FR-1.3** 顶层新增 `primaryId` 字段，标识当前主实例。
- **FR-1.4** 主实例规则：启动时第一个创建的实例为 primary；primary 被销毁时，自动指定存活实例中 **id 最小**者为新 primary。也可由 GLaDOS 通过命令指定。

### 4.2 FR-2 克隆能力

- **FR-2.1** 新增控制命令 `clone`：
  ```json
  { "cmd": "clone", "count": 2, "role": "魔理沙", "anchorId": "mascot-3" }
  ```
  - `count`：克隆数量（默认 1，上限受 `maxInstances` 限制，默认 8，可配）。
  - `role`：克隆目标角色，缺省沿用 `anchorId` 实例的 role；再缺省沿用 primary。
  - `anchorId`：克隆位置参考实例（新实例在它附近生成）；缺省为 primary。
  - 返回 `{ "ok": true, "created": ["mascot-7","mascot-8"] }`。
- **FR-2.2** 克隆受 `maxInstances` 约束（默认 8，settings.properties 可配 `Glados.MaxInstances`），超限返回 `{ ok:false, error:"instance limit reached (8)" }`。
- **FR-2.3** 克隆出的实例标记 `origin: "clone"`，primary 标记 `origin: "primary"`；若为自主增殖产物标记 `origin: "breed"`（本期托管模式仍禁用自主增殖，仅预留字段）。
- **FR-2.4** 新增命令 `dispose`（按实例销毁）：
  ```json
  { "cmd": "dispose", "target": "mascot-7" }
  ```
  同时支持 `target: "followers"`（销毁所有非 primary 实例）。
- **FR-2.5** 克隆入口唯一：托管模式下 `SplitIntoTwo`/`PullUpShimeji` 保持禁用（现状），**不提供任何 UI 手动克隆入口**（右键菜单已被禁用），克隆只由 GLaDOS 通过 `clone` 命令驱动。避免用户误触产生失控实例。

### 4.3 FR-3 事件与行为寻址（target 语义）

- **FR-3.1** `setBehavior` 新增可选 `target` 参数，取值：
  | target | 语义 |
  |---|---|
  | 缺省 / `"all"` | 全部实例（向后兼容现状） |
  | `"primary"` | 仅主实例 |
  | `"followers"` | 仅非主实例 |
  | `"nearest"` | 离鼠标最近的实例（Shimeji 侧用 `MouseInfo` 取指针） |
  | `"mascot-7"` | 指定实例 ID |
- **FR-3.2** GLaDOS 侧默认改为 `target: "primary"`（稳态与瞬时均如此），分身响应由 `followerResponse` 策略在宿主侧二次下发（`target:"followers"` + 延迟/抽样）实现。
- **FR-3.3** 事件上报补齐实例标识：
  - 内容首行改为 JSON `{"type":"click","id":"mascot-7"}`（推荐，向后兼容解析：首行非 `{` 时走旧格式）。
  - `click` 事件带 `id`：**仅用于日志/统计与"气泡挂到点中的实例"**；对话归属仍是全局（决策 A），不因 id 改变会话。
  - `move` 事件带 `id`，宿主按 id 合并坐标（而非覆盖单元素数组）。
- **FR-3.4** `move` 上报在实例数 > N（默认 3）时降级为"只上报 primary + 最近被点击的实例"，避免事件文件写爆。

### 4.4 FR-4 对话归属（问题一的落地）

> 决策 A（全局单对话）：所有实例共用一个 AI 会话，点击哪个都打开同一个对话窗口。

- **FR-4.1** **不建立** `instanceId ↔ sessionId` 映射；全进程只有一个对话会话（沿用现有 `binding().sessionId`）。
- **FR-4.2** 点击任意实例 → 打开（或聚焦）同一个 `chatWindow`；300ms 内重复点击只算一次（现有去抖保留）。
- **FR-4.3** `chatWindow` 全局单例，标题固定（如"GLaDOS 桌宠"），**不因实例变化而改标题**。
- **FR-4.4** 气泡定位跟随"当前主实例（primary）"：优先 `primaryId` 对应坐标，无则取被点击的最近实例，再兜底 `mascots[0]`。**气泡位置随实例变化，但对话内容不变**。
- **FR-4.5** 实例销毁不影响对话会话；若 primary 被销毁，新 primary 接管气泡定位。
- **FR-4.6** 产品语义需在设置页/文档写明：**分身的身体，同一个 GLaDOS 人格**，因此对话不区分实例。

### 4.5 FR-5 可观测与降级

- **FR-5.1** `/status` 增加 `instances` 计数与 `maxInstances`，宿主设置页展示"当前 N/8 个分身"。
- **FR-5.2** 实例数超阈值时，日志 WARN 并自动把 `followerResponse` 降级为 `sample`。
- **FR-5.3** 所有新增命令保持白名单校验，未知 target 返回明确错误。

## 9. 风险与缓解

| 编号 | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R-1 | 多实例时"点谁都同一个对话"可能让用户误以为是 bug | 体验理解 | 设置页/文档明示"分身的身体，同一个 GLaDOS 人格"（FR-4.6） |
| R-2 | 分身响应策略切换点（3 个）是否合适 | 视觉表现 | 做成可配 `followerResponse`；≤3 mirror、>3 sample 为默认 |
| R-3 | 实例 ID 进程内自增、重启重置；宿主若持久化 id 会失配 | 状态一致性 | 宿主每轮 `/status` 全量刷新实例清单，不跨进程持久化 id |
| R-4 | 引擎行为表条件 `totalCount<50` 与新 `maxInstances=8` 并存 | 配额语义 | 统一以 8 为产品上限；50 仅作引擎兜底不可达 |
| R-5 | 多实例同时播动画的性能（JNA 透明窗口数量） | 性能 | 8 上限 + follower 抽样；P2 实机压测 |
| R-6 | 分身共享同一个 AI 会话，用户可能期望"分身独立人格" | 产品预期 | 明确产品定位；如后续需要再开"多会话"需求（原方案 B/C） |

## 10. 决策结论（2026-11-26 已确认）

| 决策项 | 结论 | 说明 |
|---|---|---|
| **1. 对话归属** | **A. 全局单对话（保持现状）** | 点任何实例都打开同一个对话窗口；不建立实例↔会话映射。GLaDOS 侧 `onShimejiClick→openChat` 无需改动。 |
